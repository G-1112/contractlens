## 提问

> 用户上传的 DOCX 千奇百怪。我想确认一件事：
> 如果文件损坏、或者里面塞了控制字符 / 畸形 XML，
> 分析接口会怎么样？我要的不是"不崩"，而是"崩了也要告诉用户该怎么办"。

## AI 建议

AI 先给出判断标准，而不是直接改代码：

> 比"崩溃"更危险的是**不报错的错误结果**——用户会在错误结论上做法律决策。
> 所以先分类：① 未捕获异常（500/流中断）② 静默返回错误内容 ③ 明确拒绝/降级。
> 只有 ③ 是可接受的；要重点查"看似成功但实际给了错东西"的情况。

并建议用 FastAPI 的 `TestClient` 直接打真实接口，而不是只单测解析函数——
因为异常是在**流式响应生成过程中**抛出的，单测解析器测不到这条路径。

## 我如何采纳并改进

1. 构造 8 类畸形 DOCX（控制字符 0x00 / 未闭合标签 / 深嵌套 1000 层 /
   伪装扩展名 / 空文件 / 超高压缩比 …）直打 `/api/upload` 与 `/api/analyze`；
2. 上传层结论是干净的：0 个 5xx、0 信息泄漏（伪装扩展名正确 415、空文件 400）；
3. 但分析层暴露问题：`event_stream()` 的 `try` **只有 finally、没有 except**，
   `parse_file()` 抛出的 `lxml.etree.XMLSyntaxError` 直接穿透 SSE 生成器。

## 引导修 Bug

第一轮我只测了解析函数，得到"10 个 OK、3 个异常"的结果，想直接报成漏洞。
进一步检查发现**测量方式本身有问题**：合成 DOCX 没被正确读取（基线用例也返回 0 行），
那 10 个"OK"是不可信的。

我向 AI 反馈"基线都不对，结论不能用"，AI 建议：
- 先用仓库里**真实存在**的样本文件校准解析器输出（确认 `parse()` 返回的是
  `tuple (lines, has_text)`，不是我以为的对象）；
- 再改从 **HTTP 层**测，看状态码而不是看函数有没有抛异常。

校准后重测才得到可信结论：3 类畸形输入确实让异常穿透 SSE，且**客户端收不到
任何 error 事件**（前端随后调 `/api/result` 拿到 404，用户只看到"分析失败"
却不知道文件已损坏）。

修复：`try` 补 `except`，产出 `PARSE_FAILED` 事件，只回传异常类型名 + 可操作提示
（沿用既有安全口径 R-ERR-01，不泄漏内部路径/堆栈）。

## 沉淀

- 落点：`api/routers/analyze.py`（`event_stream`）、`tests/test_analyze_malformed.py`（3 项）
- 可复现验证：
  ```bash
  pytest tests/test_analyze_malformed.py -q     # 3 passed
  ```
- 教训（写入项目长期记忆）：**探测脚本先跑已知正确的基线**，
  确认基线输出非 0 再下结论；断言前先确认被测对象的真实接口，
  不要用 `getattr(x, '字段名', 默认值)` 猜——取不到就静默回退，会造出假结论。
